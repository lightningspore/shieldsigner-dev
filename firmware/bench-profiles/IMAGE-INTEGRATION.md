# One-flash zram and Rust LCD image plan

The opt-in image profiles below are implemented. The combined camera/Rust LCD runtime has passed a 23-minute GUI soak on the physical board, but a fresh persistent image boot, optical QR and physical navigation remain unverified. Keep these distinct from package compilation and packed-image checks.

## Recommended durable path

Use the existing pinned OS/SDK pipeline, with a kernel configuration change and a small external Buildroot LCD package. The repo wrapper remains the single entry point. The final output is a complete SD image, its immutable input manifest, generated artifact receipts and packed-image verification—not a live tar overlay.

1. **Prepare guarded source inputs.** Extend `scripts/configure-os-camera.py` at the existing pinned OS anchors. Before upstream `sdk_build kernel`, apply a checked Mini defconfig fragment: `CONFIG_SWAP=y`, `CONFIG_ZSMALLOC=m`, `CONFIG_ZRAM=m`, `CONFIG_CRYPTO_LZO=y`, with `CONFIG_ZRAM_WRITEBACK` and memory-tracking/debug options off. In this SDK, ZRAM *depends on* ZSMALLOC; enabling ZRAM alone is insufficient. Preserve the reviewed camera options and `MINI_CMA_SIZE=12M` Docker forwarding.
2. **Produce the new kernel receipt.** The configuration hash changes from the bench image's `a1d37e…`; do not relax its old receipt. Reuse the existing kernel-probe boundary and 190 UAPI/source assertions to generate a new exact image profile. Read back generated `.config`, DTB, kernel release and module export provenance. Verify zram, zsmalloc and the six camera modules are installed with matching vermagic. The SDK's `__PACKAGE_RESOURCES` already copies `sysdrv/out/kernel_drv_ko` into `/oem/usr/ko`; the inspected OEM prune script does not delete these zram modules. Confirm that in the actual packed rootfs.
3. **Build LCD inside the target package stage.** Add a pinned external Buildroot package using this repo's `firmware/lcd-rs` source/Cargo.lock. It must depend on the SDK host Rust toolchain and build after it exists. Reuse the flags from `firmware/lcd-rs/build-uclibc.sh`: SDK Rust 1.82, ARM GCC/sysroot, `PYO3_NO_PYTHON=1`, `armv7-unknown-linux-uclibceabihf`, locked Cargo and an isolated `CARGO_TARGET_DIR` under the build output. The camera's static musl target is unsuitable for a Python extension. Fresh builders need this toolchain bootstrap; a previously cached `.so` is not the sole reproducibility path.
4. **Install explicit hashed runtime assets.** Install the renamed `shieldsigner_lcd.abi3.so` plus `shieldsigner_lcd_driver.py` under the existing camera Python path, or a separately declared library path. Install current verified Rust camera/QR/Python sources and their notices through the existing bundle/overlay mechanism. For build-generated LCD/modules, record source/Cargo.lock/compiler/sysroot inputs and actual final ELF hashes in an image receipt; do not pretend they existed in a pre-build binary manifest. An alternative is to build and seal all binaries in an explicit preparation phase before the final image pass, but that costs an additional stage and must work from an empty cache.
5. **Start zram before the app.** A reviewed init unit such as `S20zram` can run after mount/device setup and before `S99seedsigner`. Load zsmalloc then zram, select LZO before disksize, enforce 16 MiB logical/8 MiB allocator limit, and activate only `/dev/zram0`. Keep writeback disabled. Generate the startup hash/config checks from the new module receipt: today's `enable-zram.sh` deliberately pins the old bench module hashes and old kernel config, so it must not be copied unchanged and silently bypassed. Refuse foreign/different state, wait for device readiness, and hold app startup explicitly if required setup fails.
6. **Select the LCD backend deliberately.** Current `shieldsigner_integration.py` now supports `--lcd-backend rust` / `SHIELDSIGNER_LCD_BACKEND`; the launcher can use that existing opt-in rather than duplicating the bench monkeypatch. It must select the shim before Renderer construction, enable the reviewed Small-RAM/lazy-import policy before Scan imports, and preserve the ST7789 source/GPIO/SPI guards. Do not auto-enable the GUI in the held diagnostic profile just because assets were installed. A separate reviewed normal-app startup policy must be selected for the final carrier image.
7. **Keep the final SDK boundary strict.** `camera-image-overlay.py` already installs before hardening and verifies after late SDK copies/stripping, with the finalizer immediately before mkfs. Add module/zram-init/LCD/launcher hashes and modes to that path. The SDK strip step also touches shared libraries; either preserve the exact tested LCD `.so` via a narrowly guarded path exclusion, or define and validate a post-strip artifact before hardware qualification. Do not reinterpret changed bytes as an exact-hash pass.
8. **Verify and flash once.** Extend `verify-os-image.py` packed readback to require CMA12, the new kernel/module receipt, init order/settings, executable startup modes, selected LCD backend, and current native assets. QEMU can check the actual ARM Python extension imports against the packed uClibc dependencies and run direct-data QR tests without initializing GPIO. Physical qualification must then cover cold zram activation, `/proc/swaps` showing only RAM swap, `mm_stat` limit, real GUI preview/cancellation, optical QR, buttons/smartcard and a power cycle. The image is not boot-qualified merely because it built.

## Faster complete-image option

For a near-term image with **unchanged** kernel/config, the already reproducible external-module build (`reverse-engineering/rkaiq/scripts/build-zram-modules.py`) can generate the exact bench zram modules, and the existing cached SDK can build the uClibc LCD extension. Seal those outputs with source/toolchain/module receipts into a new immutable bundle, then run the normal full-image path with an explicit pre-app zram unit and LCD backend. This is still a complete, reproducible one-flash image if the wrapper owns all preparation commands and handles a fresh builder; it must not depend on ad hoc files copied from the current board. It avoids changing the kernel receipt immediately, but retains an external-module build policy that the durable Kconfig approach removes.

Neither option requires a general-purpose live repacker. The existing unsigned CMA-only derivative remains a narrowly scoped diagnostic correction and is not the packaging mechanism for new camera/Python/LCD/zram sources.

## Cold-boot acceptance checks

Use the fully verified SD image, not a copied runtime overlay. Retain the raw and compressed SHA256 receipts and packed verifier report with the image. Flash only an identified removable card; do not overwrite the running card through ADB.

1. Boot with the reviewed base-fork display/button wiring. Confirm development ADB connects, the app starts automatically, and the development notice can be dismissed with a physical button. Verify normal colors and all buttons; backlight stays on with this wiring.
2. Read `/proc/swaps`: only `/dev/zram0` may be active. Verify `disksize` is 16777216, `mm_stat` field 4 (the allocation limit) is 8388608; `mem_limit` itself is write-only in this driver, LZO is selected, and no swap writeback device exists. Inspect the boot setup log for failure rather than assuming the init script ran.
3. Check the installed image receipt and actual native/LCD hashes against the packed report. Confirm the app selected the Rust LCD backend, Small-RAM policy and 4096 KiB MEMLOCK limit. Verify UART2 remains disabled for the GPIO42/43 buttons; PCSC is intentionally held only in this base-fork profile.
4. Open Scan and acquire a **public test QR** optically. The existing burn-address fixture is safe test data; never send funds to it. A direct decoder test or a preview frame counter does not prove optical decoding. Confirm the app recognizes the decoded type.
5. Press Back, reopen Scan at least three times, and exercise other menus. After each stop, verify the camera owner and QR worker exit and camera DMA returns to zero. A benchmark SIGTERM or API crash-recovery test does not prove physical navigation.
6. Run the real GUI/camera/Rust LCD workload for at least 20 minutes on the new image. Record frame/render counters, reader errors, reconnects, per-process PSS, MemAvailable, major faults, zram allocation and kernel OOM messages. Use the existing metadata-only bench/collector; do not publish captures or decoded wallet data.
7. Power-cycle and repeat startup, optical QR and Back/reopen. Record exact image SHA, boot ID and results. Only this provides persistent-image hardware evidence; a successful QEMU import or old-image soak is insufficient.
